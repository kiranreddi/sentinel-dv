# v2.0.0 Implementation Brief — Agent Handoff Document

**Purpose:** This document is a complete, self-contained brief for an agent (or developer) taking over
implementation of Sentinel DV v2.0.0. Read it fully before writing a single line of code.
Every feature below has been scoped against the existing codebase at v1.3.0. File paths,
schema conventions, error codes, and naming patterns are already established — follow them
exactly so the new work integrates without friction.

---

## How to Read This Document

Each feature section is structured as:
1. **What it is** — the user-facing capability
2. **Why it belongs in v2.0.0** — the DV engineering motivation
3. **Exact implementation plan** — files to create or modify, schemas to define, DB tables to add,
   MCP tools to register, tests to write
4. **Invariants to preserve** — constraints the existing architecture enforces that must not be broken

## Codebase Orientation (Read First)

Before implementing anything, understand these entry points:

| File | Role |
|---|---|
| `sentinel_dv/server.py` | All MCP tool registrations via `@mcp.tool(name=...)` + `@_tool_wrapper` |
| `sentinel_dv/tools/core.py` | Tool logic — receives `IndexStore`, returns `dict[str, Any]` |
| `sentinel_dv/indexing/store.py` | DuckDB backend — all table DDL, queries, inserts |
| `sentinel_dv/indexing/indexer.py` | Artifact scanner that populates the store |
| `sentinel_dv/schemas/` | Pydantic models used for validation in tool responses |
| `sentinel_dv/adapters/` | Per-format parsers (uvm_log, cocotb, coverage, assertions, waveform) |
| `sentinel_dv/config.py` | `SentinelDVConfig`, `SecurityLimits`, `AdaptersConfig` — all new config goes here |
| `sentinel_dv/tools/errors.py` | `ToolError` with typed `ErrorCode` literals — always raise this, never raw exceptions |
| `sentinel_dv/tools/validate.py` | `list_response`, `detail_response`, `item_response`, `validate_id`, `clamp_pagination` |
| `tests/unit/test_mcp_tools.py` | Unit tests for tool logic |
| `tests/integration/` | End-to-end tests against real demo fixtures |
| `tests/security/test_path_traversal.py` | Security tests — add path-related tests here |

**Naming conventions in use:**
- MCP tool names: `noun.verb` (e.g., `runs.list`, `coverage.summary`, `assertions.failures`)
- DB table names: plural snake_case (e.g., `assertion_failures`, `coverage_summaries`)
- Schema classes: PascalCase Pydantic BaseModel (e.g., `CoverageMetric`, `FailureEvent`)
- Error codes: SCREAMING_SNAKE from `ErrorCode` Literal in `tools/errors.py`
- Config fields: snake_case under the appropriate config sub-model

**MCP tool registration pattern (copy this exactly):**
```python
@mcp.tool(name="feature.action")
@_tool_wrapper
def feature_action(
    param: str = Field(..., description="Clear description with example value"),
    optional_param: str | None = Field(None, description="Optional. What it filters."),
    page: int = Field(1, description="Page number (1-based)"),
    page_size: int = Field(100, description="Items per page"),
) -> dict[str, Any]:
    """
    One-line summary of what this tool does.

    Returns: description of the response shape.
    Use when: describe the agent scenario that should trigger this tool.
    """
    return core.feature_action(get_store(), param, optional_param=optional_param, page=page, page_size=page_size)
```

**Architecture invariant:** The MCP server is **strictly read-only** for artifact data.
The two write-adjacent features below (job submission, replay) are implemented as
**command generation**, not execution. The server never shells out, never writes to
artifact roots, never modifies the DuckDB index from an MCP tool call.

## Feature 1: Regression Job Submission (Command Generation)

### What it is

A tool `runs.submit` that accepts a suite name, optional seed override, optional test filter,
and optional simulator hint, and returns a **ready-to-execute shell command string** that the
user (or their CI system) can run to kick off a new regression. The server does not execute
the command. It generates it from a configurable command template.

### Why it belongs here

A DV engineer's daily loop is: look at yesterday's regression → find failures → fix RTL →
re-run the suite. Right now Claude can do steps 1–3 but step 4 requires the engineer to
manually construct the LSF/SLURM/makefile command. This closes that loop. The agent can
call `runs.submit` and hand the engineer a copy-pasteable command with the right seed,
test filter, and simulator flags already filled in.

### Implementation plan

#### 1. Config — `sentinel_dv/config.py`

Add a new sub-model `SubmitConfig` inside `SentinelDVConfig`:

```python
class SimulatorTemplate(BaseModel):
    """Command template for a specific simulator."""
    simulator: str = Field(..., description="Simulator name (vcs|questa|xcelium|verilator)")
    template: str = Field(
        ...,
        description=(
            "Shell command template. Available placeholders: "
            "{suite}, {seed}, {test_filter}, {extra_args}, {artifact_root}"
        ),
    )
    default_args: str = Field(default="", description="Default extra arguments")

class SubmitConfig(BaseModel):
    """Regression job submission configuration."""
    enabled: bool = Field(default=False, description="Enable runs.submit tool")
    default_simulator: str = Field(default="vcs", description="Default simulator name")
    templates: list[SimulatorTemplate] = Field(
        default_factory=list,
        description="Per-simulator command templates",
    )
    lsf_queue: str | None = Field(None, description="LSF queue name (wraps command in bsub)")
    slurm_partition: str | None = Field(None, description="SLURM partition (wraps in sbatch)")
```

Add `submit: SubmitConfig = Field(default_factory=SubmitConfig)` to `SentinelDVConfig`.

Also add `max_command_length: int = Field(default=4096, ...)` to `SecurityLimits`.

#### 2. New schema — `sentinel_dv/schemas/submission.py`

```python
class SubmitRequest(BaseModel):
    suite: str                        # Required. Suite name from existing runs.
    simulator: str | None             # Optional. Falls back to submit.default_simulator.
    seed: int | None                  # Optional. Integer seed to reproduce a specific test.
    test_filter: str | None           # Optional. Glob or regex test name filter.
    extra_args: str | None            # Optional. Appended verbatim to the generated command.

class SubmitResponse(BaseModel):
    suite: str
    simulator: str
    seed: int | None
    command: str                      # The generated shell command. Bounded by max_command_length.
    scheduler_command: str | None     # If lsf_queue or slurm_partition configured, the wrapped form.
    dry_run: bool = True              # Always True — this server never executes commands.
    note: str                         # Reminder that this is a generated command, not executed.
```

#### 3. Tool logic — `sentinel_dv/tools/core.py`

Add function `generate_submit_command(store, suite, simulator, seed, test_filter, extra_args)`:

- Validate `suite` exists in the store (`store.count_runs()` filtered by suite > 0 or
  directly query). If suite unknown, raise `ToolError("NOT_FOUND", f"Suite '{suite}' has no indexed runs. Check runs.list for valid suite names.")`.
- Look up config `get_config().submit`. If `not config.submit.enabled`, raise
  `ToolError("PERMISSION_DENIED", "runs.submit is disabled. Set submit.enabled: true in config.yaml.")`.
- Find matching `SimulatorTemplate` for the requested simulator. If none found, raise
  `ToolError("INVALID_ARGUMENT", f"No template for simulator '{simulator}'. Available: {[t.simulator for t in config.submit.templates]}.")`.
- Interpolate the template using `str.format_map` with a safe mapping that leaves unknown
  placeholders as literal text (do not use `.format()` — user-controlled `extra_args` could
  contain braces).
- Wrap in LSF `bsub -q {queue} "{command}"` or SLURM `sbatch --partition={partition} --wrap="{command}"` if configured.
- Truncate to `max_command_length` and return `SubmitResponse`.

#### 4. Server registration — `sentinel_dv/server.py`

```python
@mcp.tool(name="runs.submit")
@_tool_wrapper
def runs_submit(
    suite: str = Field(..., description="Suite name to run (must exist in runs.list)"),
    simulator: str | None = Field(None, description="Simulator override (vcs|questa|xcelium|verilator). Defaults to submit.default_simulator in config."),
    seed: int | None = Field(None, description="Seed to fix for reproducing a specific test. Omit for random."),
    test_filter: str | None = Field(None, description="Test name glob or pattern to run a subset (e.g. 'axi_burst_*')."),
    extra_args: str | None = Field(None, description="Extra simulator arguments appended verbatim to the generated command."),
) -> dict[str, Any]:
    """
    Generate a ready-to-run regression command for a suite.

    Does NOT execute the command. Returns the shell command string for the user
    to copy-paste or pipe to their CI system.
    Use when: the engineer has reviewed failures and wants to re-run the suite
    with a seed fix, test filter, or simulator override.
    """
    return core.generate_submit_command(
        get_store(), suite=suite, simulator=simulator,
        seed=seed, test_filter=test_filter, extra_args=extra_args,
    )
```

#### 5. Demo config example — `config.example.yaml`

Add a `submit:` block showing a real VCS and Questa template so users can copy it directly:

```yaml
submit:
  enabled: true
  default_simulator: vcs
  templates:
    - simulator: vcs
      template: "make -C {artifact_root} regression SUITE={suite} SEED={seed} TESTFILTER={test_filter} VCS_ARGS='{extra_args}'"
      default_args: "+vcs+lic+wait"
    - simulator: questa
      template: "vsim -do 'run_regression.do' -G SUITE={suite} -G SEED={seed} {extra_args}"
  lsf_queue: normal
```

#### 6. Tests

- `tests/unit/test_mcp_tools.py`: test template interpolation, LSF wrapping, missing suite error,
  disabled config error, missing simulator template error, `extra_args` with braces (injection safety).
- `tests/unit/test_config.py`: test `SubmitConfig` Pydantic validation.

## Feature 2: Live Simulator Hook (State Polling Adapter)

### What it is

A new **adapter** (`sentinel_dv/adapters/live_sim.py`) that reads a well-defined
**live state file** that a running simulator writes periodically (a small JSON sidecar),
and a new MCP tool `sim.status` that returns the current simulation progress without
needing to wait for the run to finish and be indexed.

The server does **not** connect to a simulator process, does not use TCP/IPC, and does not
execute any commands. It reads a JSON file from the artifact root that the simulator's UVM
test (or a Makefile wrapper) is responsible for writing. This keeps the read-only invariant.

### Why it belongs here

Coverage closure campaigns run for hours. An engineer running a nightly wants to check
mid-run: how many tests have finished, what's the current pass rate, are there early fatals
that should trigger an abort? Today they must SSH into the compute node. With `sim.status`
Claude can answer this from the indexed live-state file.

### Implementation plan

#### 1. Live state file format (document + validate)

Create `sentinel_dv/schemas/live_sim.py`:

```python
class LiveSimProgress(BaseModel):
    """Schema for the live simulation state sidecar file."""
    suite: str
    run_id: str                        # Matches the run_id that will be indexed when done.
    simulator: str
    started_at: str                    # RFC3339
    as_of: str                         # RFC3339 — when this file was last written
    phase: Literal["compiling", "elaborating", "running", "finishing", "done", "aborted"]
    total_tests: int
    completed_tests: int
    passed_tests: int
    failed_tests: int
    active_tests: list[str]            # Names of currently running tests (bounded to 20)
    recent_errors: list[str]           # Last N UVM_ERROR/FATAL lines (bounded to 10, redacted)
    estimated_finish_at: str | None    # RFC3339 or None
```

Document the file path convention: `{artifact_root}/{suite}/live_status.json`. The simulator
wrapper (Makefile, Python script, or UVM reporting callback) is responsible for writing this
file every N seconds. Provide a reference Makefile snippet in `docs/guides/live-sim.md`.

#### 2. Adapter — `sentinel_dv/adapters/live_sim.py`

```python
class LiveSimAdapter:
    def __init__(self, artifact_roots: list[str], redactor: Redactor): ...

    def read_status(self, suite: str) -> LiveSimProgress | None:
        """
        Find and parse live_status.json under any artifact root for this suite.
        Returns None if no live file found (sim not running or not configured).
        Applies redactor to recent_errors before returning.
        Validates with LiveSimProgress — raises ToolError("INTERNAL", ...) on schema violation.
        """
```

Path resolution must use the same `_resolve_artifact_path` logic as waveform artifacts —
validate the candidate path is inside an artifact root before opening it.

#### 3. Config — `sentinel_dv/config.py`

Add to `AdaptersConfig`:
```python
live_sim: bool = Field(default=False, description="Enable live simulation status adapter")
live_sim_max_age_seconds: int = Field(
    default=300,
    description="Maximum age of live_status.json before reporting as stale",
)
```

#### 4. Tool logic — `sentinel_dv/tools/core.py`

Add `get_sim_status(store, suite)`:
- Check `get_config().adapters.live_sim` — if False, raise `ToolError("PERMISSION_DENIED", "Live sim adapter disabled. Set adapters.live_sim: true in config.yaml.")`.
- Instantiate `LiveSimAdapter` with config artifact roots and default redactor.
- Call `read_status(suite)`. If None, raise `ToolError("NOT_FOUND", f"No live_status.json found for suite '{suite}'. Is the simulation running with the live-sim adapter enabled?")`.
- Check `as_of` age against `live_sim_max_age_seconds`. If stale, return the data but include
  `"stale": true, "stale_seconds": N` in the response so the agent can warn the user.
- Return `detail_response({**status.model_dump(), "stale": False})`.

#### 5. Server registration — `sentinel_dv/server.py`

```python
@mcp.tool(name="sim.status")
@_tool_wrapper
def sim_status(
    suite: str = Field(..., description="Suite name to check live status for"),
) -> dict[str, Any]:
    """
    Get live simulation progress for a currently-running suite.

    Reads a sidecar file written by the simulator wrapper — does not connect
    to the simulator process directly.
    Returns phase, test counts, active tests, and recent errors.
    Use when: checking mid-run progress without waiting for indexing to complete.
    """
    return core.get_sim_status(get_store(), suite=suite)
```

#### 6. Reference simulator wrapper

Create `examples/live_sim_writer.py` — a Python script that a Makefile can call every
30 seconds to write the `live_status.json`. Include a Makefile snippet in the docstring.
This is not part of the server — it's a reference implementation for users.

#### 7. Tests

- `tests/unit/test_live_sim.py`: parse valid live state file, stale detection, missing file,
  schema violation, path traversal attempt via suite name (`../../etc/passwd`).
- `tests/integration/`: add a fixture `demo/live_sim/counter_suite/live_status.json` and an
  integration test that calls `sim.status`.

## Feature 3: SVA / Formal Property Status

### What it is

Two new MCP tools — `assertions.sva_status` and `assertions.vacuity` — that expose:

1. **`assertions.sva_status`**: for each SVA property indexed, whether it **fired** (antecedent
   matched and consequent was checked), **passed**, **failed**, **never triggered** (vacuous),
   or was **disabled** during the run. Requires a new `sva_runs` table.

2. **`assertions.vacuity`**: lists all assertions that were enabled but never had their
   antecedent triggered across a given run — the "dead assertion" problem. These are assertions
   that give false confidence because they never actually checked anything.

### Why it belongs here

In any UVM/SVA regression, vacuous assertion passes are a silent quality problem. An assertion
like `assert property (@clk axi_valid |-> ##[1:4] axi_ready)` shows 0 failures but may have
never been triggered if the stimulus never drove `axi_valid`. Today there is no tool to surface
this. An agent with `assertions.vacuity` can proactively flag: "12 AXI protocol assertions
never fired in this run — your stimulus may not be exercising the AXI bus."

### Implementation plan

#### 1. New DB table — `sentinel_dv/indexing/store.py`

Add to `_create_schema()`:

```sql
CREATE TABLE IF NOT EXISTS sva_run_status (
    id INTEGER PRIMARY KEY,
    run_id TEXT NOT NULL,
    test_id TEXT NOT NULL,
    assertion_id TEXT NOT NULL,
    status TEXT NOT NULL,           -- 'fired_pass' | 'fired_fail' | 'vacuous' | 'disabled' | 'unknown'
    fire_count INTEGER NOT NULL DEFAULT 0,
    pass_count INTEGER NOT NULL DEFAULT 0,
    fail_count INTEGER NOT NULL DEFAULT 0,
    vacuous_count INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX IF NOT EXISTS idx_sva_run ON sva_run_status(run_id);
CREATE INDEX IF NOT EXISTS idx_sva_test ON sva_run_status(test_id);
CREATE INDEX IF NOT EXISTS idx_sva_assertion ON sva_run_status(assertion_id);
CREATE INDEX IF NOT EXISTS idx_sva_status ON sva_run_status(status);
```

Add store methods:
```python
def insert_sva_status(self, run_id, test_id, assertion_id, status, fire_count, pass_count, fail_count, vacuous_count) -> None: ...
def query_sva_status(self, run_id=None, test_id=None, assertion_id=None, status=None, page=1, page_size=100) -> tuple[list[dict], int]: ...
def query_vacuous_assertions(self, run_id, page=1, page_size=100) -> tuple[list[dict], int]: ...
```

`query_vacuous_assertions` returns assertions where `status = 'vacuous' OR (fire_count = 0 AND status != 'disabled')`,
joined with the `assertions` table to return the assertion name, scope, and file alongside the status.

#### 2. New schema — `sentinel_dv/schemas/assertions.py` additions

Add to the existing assertions schema file:


## Feature 4: Seed Replay Command Generation

### What it is

A tool `tests.replay` that takes a `test_id` and returns a **complete, ready-to-run shell
command** to reproduce that exact test — simulator binary, test name, seed, UVM plusargs,
and optional LSF/SLURM wrapper — all reconstructed from what was indexed at run time.

### Why it belongs here

The `tests.get` tool already returns `seed`, `sim_vendor`, `sim_version`, `dut_top`, and
`name`. The seed is useless to an engineer unless they can translate it into the exact command
their makefile expects. This tool does that translation using the same template system as
Feature 1, but at the individual test level rather than the suite level.

### Implementation plan

#### 1. Config extension — `sentinel_dv/config.py`

Add an optional `replay_template` to `SimulatorTemplate`:

```python
class SimulatorTemplate(BaseModel):
    ...
    replay_template: str | None = Field(
        None,
        description=(
            "Template for single-test replay. Placeholders: "
            "{test_name}, {seed}, {dut_top}, {suite}, {extra_args}, {artifact_root}. "
            "Falls back to template with TESTFILTER={test_name} SEED={seed} if not set."
        ),
    )
```

#### 2. New schema — `sentinel_dv/schemas/submission.py` additions

```python
class ReplayResponse(BaseModel):
    test_id: str
    test_name: str
    suite: str
    simulator: str
    seed: int | None
    dut_top: str | None
    command: str                      # Bounded replay command
    scheduler_command: str | None     # LSF/SLURM wrapped form
    dry_run: bool = True
    note: str
    warning: str | None               # Set if seed is None — replay may not be deterministic
```

#### 3. Tool logic — `sentinel_dv/tools/core.py`

Add `generate_replay_command(store, test_id, extra_args)`:

- Look up test via `store.get_test(test_id)`. If not found, raise `ToolError("NOT_FOUND", ...)`.
- Look up the run via `store.get_run(test["run_id"])` to get the suite name.
- Get `sim_vendor` from the test record. Match against configured templates.
  If `sim_vendor` is None or no template matches, raise `ToolError("INVALID_ARGUMENT",
  f"No simulator template for '{sim_vendor}'. Configure submit.templates in config.yaml.")`.
- Use `replay_template` if set, otherwise fall back to the suite template with
  `TESTFILTER={test_name} SEED={seed}`.
- If `seed` is None, include `warning: "This test has no indexed seed — replay may not reproduce the exact failure."`.
- Wrap in LSF/SLURM if configured.

#### 4. Server registration — `sentinel_dv/server.py`

```python
@mcp.tool(name="tests.replay")
@_tool_wrapper
def tests_replay(
    test_id: str = Field(..., description="Test identifier (from tests.list or tests.get) to generate replay command for"),
    extra_args: str | None = Field(None, description="Additional simulator arguments to append"),
) -> dict[str, Any]:
    """
    Generate a command to reproduce a specific test with its exact seed.

    Reconstructs the simulator invocation from indexed test metadata.
    Does NOT execute the command. Returns it for the user to run.
    Use when: a test failed and the engineer wants to reproduce it locally
    or submit a single-test re-run to the farm.
    """
    return core.generate_replay_command(get_store(), test_id=test_id, extra_args=extra_args)
```

#### 5. Tests

- Unit: seed present, seed absent (warning), sim_vendor None, missing template.
- Integration: index a test from a VCS fixture that has seed, call `tests.replay`,
  assert command contains the seed value.

## Feature 5: Coverage Closure Guidance

### What it is

A tool `coverage.gaps` that analyzes the coverage database for a run and returns:
1. **Uncovered bins** — coverpoints with `covered < 100%` and their `bins_missed` lists.
2. **Recommended test patterns** — heuristic suggestions for what kind of stimulus would
   cover each uncovered bin, derived from the bin name, scope, and any assertion tag metadata.
3. **Priority ordering** — gaps ordered by how many other metrics share the same scope
   (a scope with 5 uncovered coverpoints is higher priority than one with 1).

This is purely analytical — it reads `coverage_summaries` and `assertions` from DuckDB
and applies deterministic heuristics. It does not call an LLM internally.

### Why it belongs here

`coverage.summary` already shows what is covered. The missing step is telling the engineer
*what to do about it*. A DV engineer looking at 87.5% AXI functional coverage wants to know:
"which bins are missing, and what test stimulus closes them?" Today that requires manually
reading the coverage report and cross-referencing with the testplan. `coverage.gaps` does
this cross-reference automatically from what's already indexed.

### Implementation plan

#### 1. New schema — `sentinel_dv/schemas/coverage.py` additions

```python
class CoverageGap(BaseModel):
    """A single uncovered coverpoint with closure recommendations."""
    run_id: str
    kind: CoverageKind
    metric_name: str                  # e.g. "axi.awlen_bins"
    scope: str                        # e.g. "tb.env.axi_master_agent"
    covered_pct: float                # e.g. 87.5
    bins_missed: list[str]            # e.g. ["awlen_15", "awlen_14"]
    priority: int                     # 1 = highest. Based on scope gap density.
    recommendations: list[str]        # Heuristic suggestions (see below)

class CoverageGapsResponse(BaseModel):
    run_id: str
    kind: str | None                  # Filter applied, or None for all kinds
    total_gaps: int
    fully_covered_metrics: int
    uncovered_metrics: int
    gaps: list[CoverageGap]           # Bounded to max_coverage_gaps (new security limit)
    analysis_note: str                # e.g. "3 scopes account for 80% of uncovered bins"
```

#### 2. Heuristic recommendation engine — `sentinel_dv/normalization/coverage_hints.py`

Create a new file. This module maps bin names and scope patterns to recommendation strings
using a lookup table approach. Do **not** use an LLM. Examples:

```python
SCOPE_HINTS = {
    "axi": "Generate AXI transactions with {bin_name} to exercise this coverpoint.",
    "apb": "Drive APB transfers targeting {bin_name}.",
    "fifo": "Fill FIFO to condition {bin_name} to hit this bin.",
}

BIN_NAME_PATTERNS = [
    (r"overflow", "Drive stimulus that causes overflow condition: {bin_name}"),
    (r"empty",    "Ensure {scope} reaches empty state"),
    (r"full",     "Ensure {scope} reaches full/saturation state"),
    (r"idle",     "Include idle cycles between transactions"),
    (r"max|MAX",  "Drive maximum-value stimulus for {bin_name}"),
    (r"min|MIN",  "Drive minimum-value stimulus for {bin_name}"),
    (r"error|ERR","Inject error conditions targeting {bin_name}"),
    (r"wrap",     "Use wrapping burst type to exercise {bin_name}"),
    (r"incr",     "Use incrementing burst type to exercise {bin_name}"),
    (r"burst",    "Generate burst transactions to cover {bin_name}"),
]

def generate_recommendations(metric_name: str, scope: str, bins_missed: list[str]) -> list[str]:
    """Return heuristic recommendation strings for uncovered bins."""
    ...
```

Add `max_coverage_gaps: int = Field(default=100, ge=1, le=500)` to `SecurityLimits`.

#### 3. Tool logic — `sentinel_dv/tools/core.py`

Add `get_coverage_gaps(store, run_id, kind=None, min_covered_pct=None, page=1, page_size=50)`:

- `validate_id(run_id, "run_id")` then verify run exists.
- Query all `coverage_summaries` for the run (with optional `kind` filter).
- For each summary, iterate `metrics`. Collect metrics where `covered < 100.0` and
  `bins_missed` is non-empty.
- Compute `priority` per scope: count how many uncovered metrics share the same scope prefix
  (first two dot-separated components of `scope`). Scopes with more uncovered metrics get
  lower priority number (higher priority).
- Sort gaps by `priority ASC`, then `covered_pct ASC` (most uncovered first within same priority).
- For each gap, call `generate_recommendations(metric_name, scope, bins_missed)`.
- Apply pagination. Clamp to `max_coverage_gaps`.
- Return `CoverageGapsResponse`.

Optional parameter `min_covered_pct: float | None` — if set, only return gaps where
`covered < min_covered_pct`. Useful for "show me only metrics below 50% coverage."

#### 4. Server registration — `sentinel_dv/server.py`

```python
@mcp.tool(name="coverage.gaps")
@_tool_wrapper
def coverage_gaps(
    run_id: str = Field(..., description="Run identifier to analyze coverage gaps for"),
    kind: str | None = Field(None, description="Coverage kind filter: functional|code|assertion|toggle|fsm"),
    min_covered_pct: float | None = Field(None, description="Only return gaps below this coverage percentage (0-100). E.g. 80.0 shows metrics below 80% covered."),
    page: int = Field(1, description="Page number"),
    page_size: int = Field(50, description="Items per page (max 100)"),
) -> dict[str, Any]:
    """
    Analyze coverage gaps for a run and suggest closure stimulus.

    Returns uncovered coverpoints ordered by priority (scopes with more gaps first),
    with heuristic recommendations for what stimulus would close each gap.
    Use when: driving coverage closure, identifying what tests or sequences to add next,
    or reporting to a coverage closure review meeting.
    """
    return core.get_coverage_gaps(
        get_store(), run_id=run_id, kind=kind,
        min_covered_pct=min_covered_pct, page=page, page_size=page_size,
    )
```

#### 5. Tests

- Unit: metrics with `covered=100.0` excluded, priority ordering correct, `min_covered_pct`
  filter works, recommendation strings generated for known bin patterns, empty result when
  all metrics covered.
- Integration: index a coverage fixture with a mix of covered/uncovered bins (the existing
  `demo/*/coverage/coverage.json` fixtures work), call `coverage.gaps`, assert at least one
  gap is returned with non-empty recommendations.
- Add a fixture where all bins are covered — assert `total_gaps=0` and `fully_covered_metrics > 0`.

## Cross-Cutting Requirements for All Features

These apply to every feature above without exception.

### Tool annotations

Every new `@mcp.tool` must include these keyword arguments on the decorator:

```python
@mcp.tool(
    name="...",
    annotations={
        "readOnlyHint": True,       # All tools are read-only
        "destructiveHint": False,
        "idempotentHint": True,
    }
)
```

The `runs.submit` and `tests.replay` tools generate commands but do not execute them —
they are still read-only from the server's perspective.

### Output schema

Every new tool response must define an `outputSchema` dict in the `@mcp.tool` call.
Study the FastMCP documentation for the exact syntax. At minimum, document the top-level
keys and their types. This is what allows MCP clients to understand responses without
calling the tool.

### Error messages must be actionable

Every `ToolError` raise must follow this pattern:
- Say **what went wrong** (the factual condition).
- Say **what to do about it** (the corrective action).
- Reference the exact config key or tool name to use.

Example:
```python
# Bad:
raise ToolError("NOT_FOUND", "Suite not found")

# Good:
raise ToolError(
    "NOT_FOUND",
    f"Suite '{suite}' has no indexed runs. "
    f"Check available suites with runs.list, or verify the suite name in your config.yaml artifact_roots."
)
```

### Security — command injection prevention

Features 1 and 4 generate shell commands from user-supplied `extra_args`. Use this pattern:

```python
import shlex

safe_args = shlex.quote(extra_args) if extra_args else ""
```

Never use `subprocess`, `os.system`, or any shell execution. The server must not execute
the generated commands under any circumstances.

Suite names and test names used in templates must be validated against a pattern before
interpolation:

```python
import re
if not re.fullmatch(r"[a-zA-Z0-9_\-\.]+", suite):
    raise ToolError("INVALID_ARGUMENT", f"Suite name contains invalid characters: '{suite}'")
```

### Existing bug fixes (implement alongside v2.0.0 features)

These were identified in the v1.3.0 review and must be fixed in this release:

**Fix 1 — Race condition in sequential ID generation (`store.py`):**
The pattern `SELECT COALESCE(MAX(id), 0) + 1 FROM assertion_failures` is used in multiple
`insert_*` methods. Replace with DuckDB `SEQUENCE`:

```sql
CREATE SEQUENCE IF NOT EXISTS seq_assertion_failure_id START 1;
CREATE SEQUENCE IF NOT EXISTS seq_evidence_id START 1;
CREATE SEQUENCE IF NOT EXISTS seq_coverage_id START 1;
CREATE SEQUENCE IF NOT EXISTS seq_sva_status_id START 1;  -- for new table
```

Then use `nextval('seq_assertion_failure_id')` in INSERT statements.
Run a migration in `_create_schema()` using `CREATE SEQUENCE IF NOT EXISTS` so existing DBs
are not broken.

**Fix 2 — `resolve_config` demo fallback must warn loudly:**
```python
# Current (silently uses demo data):
if demo_root.is_dir():
    return SentinelDVConfig(artifact_roots=[str(demo_root)], ...)

# Fixed (warn on stderr, document the fallback):
if demo_root.is_dir():
    import warnings
    warnings.warn(
        "No config.yaml found. Falling back to demo data at {demo_root}. "
        "This is for development only. Set SENTINEL_DV_CONFIG or pass --config for production.",
        UserWarning,
        stacklevel=2,
    )
    return SentinelDVConfig(artifact_roots=[str(demo_root)], ...)
```
